How to read a Lean function definition

Lean can put several kinds of parameters into one line. The punctuation says who supplies each one.

Start with this definition:

def equal {α : Type} [DecidableEq α] (a b : α) : Bool :=
  decide (a = b)

We will give the square-bracket parameter a name so that every part is visible:

def equal
    {α : Type}
    [d : DecidableEq α]
    (a b : α)
    : Bool :=
  decide (a = b)

Read it as:

Define equal. It works for an inferred type α. Lean must find an equality decision function d for that type. The caller passes a and b, and the result is a Bool.

The whole line at a glance

SyntaxDeclaresWho supplies it?
def equala definition named equalthis line introduces it

:=the start of the bodyeverything after it computes the result

The braces are not a block, and the brackets are not an array. They select how Lean obtains function arguments.

{α : Type} — infer the type argument

{α : Type}
  • α is an identifier. We could call it T instead.
  • Type says that α itself is a type, such as Nat, Bool, or Thread1D.
  • Curly braces make this argument implicit: Lean tries to infer it from later arguments.

Curly braces can make any parameter implicit. This one happens to be a type parameter because its type is Type.

This call makes the hidden argument visible:

equal (α := Nat) 10 20

Most of the time we omit it:

equal 10 20

This α is the part nearest to a generic type parameter such as Rust’s T.

[d : DecidableEq α] — search for a value

[d : DecidableEq α]

d is not another type parameter. It is a value whose type is DecidableEq α. Square brackets tell Lean to find and insert that value through instance search.

The original [DecidableEq α] leaves this value unnamed. Writing [d : DecidableEq α] only gives it a name that we can use in the explanation.

DecidableEq α is an abbreviation for this function type:

(left right : α) → Decidable (left = right)

The arrow reads “returns”: after receiving left and right, the function returns their equality decision.

Therefore d is itself a function:

d a b
-- : Decidable (a = b)

Lean chooses and inserts d while elaborating the call. The selected function can still compare the actual a and b values when the program runs.

The later chapter Dissecting deriving DecidableEq explains what that decision contains and how Lean generates d.

(a b : α) — receive the ordinary arguments

(a b : α)

This is compact notation for:

(a : α) (b : α)

Both are explicit arguments, so the caller passes both values.

They are also curried: equal a is a valid partial call that returns a function waiting for b.

Lean applies functions with spaces. equal 10 20 is the Lean counterpart of equal(10, 20) in languages that use parentheses and commas at the call site.

: Bool := — state the result and begin the body

: Bool :=
  • The colon reads “has type.” The result has type Bool.
  • := reads “is defined as.” The function body follows it.

decide (a = b) — turn the proposition into a Boolean

decide (a = b)

Function application still uses a space here. The parentheses group the entire equality expression into the one argument passed to decide.

In Lean, a = b is a proposition. It has type Prop; it is not already a Bool.

The chapter Propositions as types explains why a proposition can itself appear as the type in a declaration such as h : p.

decide turns a decidable proposition into a Boolean. To do that here, it needs a value of type:

Decidable (a = b)

The instance parameter d produces exactly that value when applied to a and b. Lean fills in the hidden argument to decide with d a b.

Make the hidden arguments visible

Here is the same idea with every argument passed directly:

def equalExplicit
    (α : Type)
    (d : DecidableEq α)
    (a b : α)
    : Bool :=
  @decide (a = b) (d a b)

The @ exposes decide’s normally hidden instance argument, which we fill directly with d a b.

Likewise, this ordinary call:

equal (α := Nat) 10 20

can be written with its hidden argument positions exposed:

@equal Nat (inferInstance : DecidableEq Nat) 10 20

inferInstance asks Lean to perform instance search at that position.

Nearest Rust reading

At the level of intent, the definition is near:

#![allow(unused)]
fn main() {
fn equal<T>(a: T, b: T) -> bool
where
    T: PartialEq,
{
    a == b
}
}

The syntax correspondence is:

LeanNearest Rust syntax
{α : Type}<T>
[DecidableEq α]where T: PartialEq

This is only a syntax and usage comparison. Rust’s equality operation returns a bool; Lean’s DecidableEq first produces a decision carrying proof evidence, and decide reduces that answer to Bool. Rust’s PartialEq may implement a custom relation; Lean’s DecidableEq must decide Lean’s built-in equality and support its answer with checked evidence.
