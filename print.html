How the pieces fit

The short version:

Elan chooses.
Lake orchestrates.
Lean checks and compiles.

lean — roughly rustc

  • Reads .lean source files.
  • Elaborates convenient syntax into precise core terms.
  • Type-checks programs.
  • Sends theorem declarations through Lean’s small trusted kernel.
  • Produces .olean compiled modules.
  • Can also produce code used by native executables.

The important difference:

Rust build: program must type-check
Lean build: program and every theorem proof must type-check
  • A broken proof is a build error.
  • There is no separate “proof build” for ordinary Lean development.

elan — almost exactly rustup

  • Installs Lean toolchains.
  • Lets different projects use different Lean versions.
  • Reads the nearest lean-toolchain file automatically.
  • Provides proxy commands such as lean and lake on PATH.

  • Creates projects.
  • Resolves package dependencies.
  • Tracks Lean module dependencies.
  • Builds libraries and executables incrementally.

How to read a Lean function definition

Lean can put several kinds of parameters into one line. The punctuation says who supplies each one.

Start with this definition:

def equal {α : Type} [DecidableEq α] (a b : α) : Bool :=
  decide (a = b)

We will give the square-bracket parameter a name so that every part is visible:

def equal
    {α : Type}
    [d : DecidableEq α]
    (a b : α)
    : Bool :=
  decide (a = b)

Read it as:

Define equal. It works for an inferred type α. Lean must find an equality decision function d for that type. The caller passes a and b, and the result is a Bool.

The whole line at a glance

SyntaxDeclaresWho supplies it?
def equala definition named equalthis line introduces it
{α : Type}an implicit type parameterLean normally infers it
[d : DecidableEq α]an implicit instance valueLean searches for it
(a b : α)two ordinary value parametersthe caller passes them
: Boolthe result typethe definition promises it
:=the start of the bodyeverything after it computes the result

The braces are not a block, and the brackets are not an array. They select how Lean obtains function arguments.

{α : Type} — infer the type argument

{α : Type}
  • α is an identifier. We could call it T instead.
  • Type says that α itself is a type, such as Nat, Bool, or Thread1D.
  • Curly braces make this argument implicit: Lean tries to infer it from later arguments.

Curly braces can make any parameter implicit. This one happens to be a type parameter because its type is Type.

This call makes the hidden argument visible:

equal (α := Nat) 10 20

Most of the time we omit it:

equal 10 20

This α is the part nearest to a generic type parameter such as Rust’s T.

[d : DecidableEq α] — search for a value

[d : DecidableEq α]

d is not another type parameter. It is a value whose type is DecidableEq α. Square brackets tell Lean to find and insert that value through instance search.

The original [DecidableEq α] leaves this value unnamed. Writing [d : DecidableEq α] only gives it a name that we can use in the explanation.

DecidableEq α is an abbreviation for this function type:

(left right : α) → Decidable (left = right)

The arrow reads “returns”: after receiving left and right, the function returns their equality decision.

Therefore d is itself a function:

d a b
-- : Decidable (a = b)

Lean chooses and inserts d while elaborating the call. The selected function can still compare the actual a and b values when the program runs.

The later chapter Dissecting deriving DecidableEq explains what that decision contains and how Lean generates d.

(a b : α) — receive the ordinary arguments

(a b : α)

This is compact notation for:

(a : α) (b : α)

Both are explicit arguments, so the caller passes both values.

They are also curried: equal a is a valid partial call that returns a function waiting for b.

Lean applies functions with spaces. equal 10 20 is the Lean counterpart of equal(10, 20) in languages that use parentheses and commas at the call site.

: Bool := — state the result and begin the body

: Bool :=
  • The colon reads “has type.” The result has type Bool.
  • := reads “is defined as.” The function body follows it.

decide (a = b) — turn the proposition into a Boolean

decide (a = b)

Function application still uses a space here. The parentheses group the entire equality expression into the one argument passed to decide.

In Lean, a = b is a proposition. It has type Prop; it is not already a Bool.

The chapter Propositions as types explains why a proposition can itself appear as the type in a declaration such as h : p.

decide turns a decidable proposition into a Boolean. To do that here, it needs a value of type:

Decidable (a = b)

The instance parameter d produces exactly that value when applied to a and b. Lean fills in the hidden argument to decide with d a b.

Make the hidden arguments visible

Here is the same idea with every argument passed directly:

def equalExplicit
    (α : Type)
    (d : DecidableEq α)
    (a b : α)
    : Bool :=
  @decide (a = b) (d a b)

The @ exposes decide’s normally hidden instance argument, which we fill directly with d a b.

Likewise, this ordinary call:

equal (α := Nat) 10 20

can be written with its hidden argument positions exposed:

@equal Nat (inferInstance : DecidableEq Nat) 10 20

inferInstance asks Lean to perform instance search at that position.

Nearest Rust reading

At the level of intent, the definition is near:

#![allow(unused)]
fn main() {
fn equal<T>(a: T, b: T) -> bool
where
    T: PartialEq,
{
    a == b
}
}

The syntax correspondence is:

LeanNearest Rust syntax
{α : Type}<T>
[DecidableEq α]where T: PartialEq
(a b : α)(a: T, b: T)
: Bool-> bool
:= body{ body }

This is only a syntax and usage comparison. Rust’s equality operation returns a bool; Lean’s DecidableEq first produces a decision carrying proof evidence, and decide reduces that answer to Bool. Rust’s PartialEq may implement a custom relation; Lean’s DecidableEq must decide Lean’s built-in equality and support its answer with checked evidence.

Pocket grammar

def name {inferred arguments} [searched-for arguments]
    (explicit arguments) : result type :=
  body

{ }   Lean infers
[ ]   Lean searches
( )   the caller passes
:     “has type”
:=    “is defined as”

fun n => n — construct a function

The Lean Lab examples connect ordinary functions to proofs. Start with:

def keepNumber : Nat → Nat := fun n => n

fun n => n creates an anonymous function: a function expression that does not declare a name. Read it as “take an argument called n, and return n.” The definition gives that function the name keepNumber.

The general pattern is fun argument => body. The first n names the parameter; the final n is the expression returned. Lean infers that n has type Nat from the expected function type Nat → Nat.

This is another way to write the same definition:

def keepNumber (n : Nat) : Nat := n

The two arrows have different jobs:

SyntaxMeaning
Nat → Nata type: functions taking a Nat and returning a Nat
fun n => na function expression: take n and return it

The => separates the anonymous function’s parameters from its body. This notation is also called a lambda expression.

Read a theorem as parameters, conclusion, and proof

For the theorem declarations below, use this grammar:

theorem name (inputs and assumptions) : conclusion := proof
  • Before the outer colon: parameters, including any proof assumptions.
  • Between that colon and :=: the proposition to prove, or conclusion.
  • After :=: the proof term, or a tactic block that constructs it.

Parameters can contain their own colons. In (hp : P), the colon says that hp has type P. The colon after the parameter groups introduces the conclusion. Assumptions are also inputs: they are proof inputs.

keepProof — return the proof you receive

theorem keepProof (P : Prop) : P → P := fun hp => hp
PartRole
theoremthe keyword
keepProofthe theorem’s name
(P : Prop)an input: a proposition
: P → Pthe conclusion: if P, then P
:= fun hp => hpthe proof: take a proof of P and return it

Declaring P : Prop does not assume that P is true. There is no proof assumption among this declaration’s parameters. The body introduces one locally: Lean reads fun hp => hp here as fun (hp : P) => hp.

To prove P → P, temporarily assume a proof hp : P, then use that same proof to establish P. This proves the implication without needing a proof of P beforehand.

The tactic version does the same thing:

example (P : Prop) : P → P := by
  intro hp
  exact hp

intro hp introduces the local assumption hp : P and leaves the goal P. exact hp supplies the proof of that goal.

applyProof — use a proof of an implication

theorem applyProof (P Q : Prop) (hpq : P → Q) (hp : P) : Q :=
  hpq hp
PartRole
(P Q : Prop)inputs: two propositions
(hpq : P → Q)an assumption: a proof that P implies Q
(hp : P)another assumption: a proof of P
: Qthe conclusion
:= hpq hpthe proof: apply hpq to hp

The conclusion is only Q. The preceding (hp : P) is still a parameter, just like (hpq : P → Q).

hpq hp is function application. The function hpq takes a proof of P, and hp is such a proof. The result is a proof of Q.

This is the Curry–Howard correspondence at work: a proof of an implication is a function from proofs of its premise to proofs of its conclusion.

One concrete use

example : 2 + 2 = 4 := rfl
example : 2 + 2 = 4 := keepProof (2 + 2 = 4) rfl

#eval keepNumber 42
-- 42

In the second proof, (2 + 2 = 4) supplies the proposition P, and rfl supplies a proof of it. keepProof returns that proof, just as keepNumber returns the number it receives.

Propositions as types — reading p : Prop and h : p

The whole idea

As a first mental model, read Prop as the collection of all propositions:

Prop : Type
└── p : Prop      one proposition, which is also a type
    └── h : p     one proof/value of that proposition

More precisely, Prop is Lean’s universe of propositions, not a runtime collection.

Read p in both directions:

  • Looking up, p is a term/value of Prop: a proposition, not a proof.
  • Looking down, p is the type of h, and h is a proof/value of p.

One concrete example

def p : Prop := (2 : Nat) + 2 = 4

theorem h : p := rfl

Substituting the definition of p makes the second line read:

theorem h : (2 : Nat) + 2 = 4 := rfl

So the names refer to different things:

p = the proposition “2 + 2 = 4”
h = a proof of that proposition

p is not h, just as Nat is not 3.

Why p can appear after a colon

The right-hand side of : is still a type in Lean:

h : p

This is valid because every proposition is a type. Here p is one such proposition/type.

The same pattern appears with ordinary data:

Nat : Type          p : Prop
3   : Nat           h : p
  • Nat is a term in the universe Type, and it is the type of 3.
  • p is a term in the universe Prop, and it is the type of h.

Lean uses the word term at both levels. A term whose type is a universe such as Type or Prop is itself a type. This does not mean that an arbitrary runtime value can be used as a type.

Read Decidable with that model

class inductive Decidable (p : Prop) where
  | isFalse (h : Not p) : Decidable p
  | isTrue  (h : p)     : Decidable p

Read each binder directly:

  • (p : Prop) chooses one proposition/type.
  • (h : p) supplies a proof of that proposition.
  • (h : Not p) supplies a proof that the proposition leads to a contradiction.
  • Decidable p is the type of a proved yes-or-no answer about p.
Decidable p
├── isTrue  h    with h : p
└── isFalse h    with h : Not p

The nearest surface Rust reading is Decidable<P>. Rust’s P is a type parameter; Lean’s p is a term of Prop and is itself a type. The parameter position looks similar, but ordinary Rust has no built-in proposition/proof relationship.

What changes across programming languages

This distinction is not “functional versus non-functional,” and it is not a measure of how strongly typed a language is. It comes from the kind of type system the language has.

LanguageUsual relationship between types and values
Rust, Java, C#Keep the type and value levels separate in ordinary code
HaskellUsually keeps terms and types separate; kinds and extensions add type-level programming
Lean, Agda, Coq, IdrisUse dependent types and universes; types are terms, and terms can occur inside types

Rust’s const generics allow a restricted form of values appearing in types:

#![allow(unused)]
fn main() {
struct Buffer<const N: usize> {
    bytes: [u8; N],
}
}

Here N affects a type, but this is much narrower than Lean’s dependent type system. Rust still does not let an arbitrary proposition term become the type of its proofs.

Haskell is functional but ordinarily maintains a term/type split. Lean is also functional, but the relevant feature here is dependent typing, not functional programming itself.

Pocket model

Prop       the universe of propositions
p : Prop   one proposition/type
h : p      one proof/value of p

For the larger hierarchy around Prop, continue to Type universes. To follow this idea through equality decisions, see Dissecting deriving DecidableEq.

Type universes — the nested-circle picture

The picture

Lean’s universes are easiest to picture as filled, nested circles:

  • The center contains propositions.
  • Each outer level can use everything from the levels inside it.
  • Moving outward also lets Lean talk about the previous universe itself.

The same picture in terminal-friendly ASCII:

+------------------------------- Type 2 --------------------------------+
| +----------------------------- Type 1 ------------------------------+ |
| | +--------------------------- Type 0 ----------------------------+ | |
| | |         Nat · Bool · Thread1D · Prop                          | | |
| | |  +------------------------- Prop --------------------------+  | | |
| | |  |      True · False · 2 = 2 · x < array.size              |  | | |
| | |  +---------------------------------------------------------+  | | |
| | +---------------------------------------------------------------+ | |
| +-------------------------------------------------------------------+ |
+-----------------------------------------------------------------------+

This is a type-checking model, not a picture of runtime memory or literal set-theoretic containers.

Read the hierarchy as a chain

rfl
 │ proves
 ▼
(2 = 2)
 │ is a proposition in
 ▼
Prop
 │ lives in
 ▼
Type 0
 │ lives in
 ▼
Type 1
 │ lives in
 ▼
Type 2

In Lean notation:

rfl     : (2 = 2)
(2 = 2) : Prop
Prop    : Type 0
Type 0  : Type 1
Type 1  : Type 2
  • A term has a type: rfl : 2 = 2.
  • A proposition is a type in Prop: (2 = 2) : Prop.
  • A small data type lives in Type 0: Nat : Type 0.
  • A universe lives one level higher: Type 0 : Type 1.

Type with no number means Type 0.

The circles overlap on purpose

The universes are cumulative:

Type 0  ──usable as──▶  Type 1  ──usable as──▶  Type 2
  • Nat naturally lives in Type 0.
  • Lean may also use Nat where a type from Type 1 or Type 2 is expected.
  • The outer levels therefore do not contain completely different types.
  • A useful approximation is Type 0 ⊆ Type 1 ⊆ Type 2.

Think nested filled circles, not separate rings:

Good:  [ Type 2 [ Type 1 [ Type 0 [ Prop ] ] ] ]

Wrong: [ Prop ]  [ Type 0 ]  [ Type 1 ]  [ Type 2 ]

Why Lean keeps adding levels

Letting the universe of types contain itself would permit dangerous self-reference:

Not allowed

Type 0 : Type 0

Lean places each universe in the next one instead:

Type 0 : Type 1
Type 1 : Type 2
Type 2 : Type 3
  • This hierarchy prevents the logical paradoxes caused by Type : Type.
  • Most ordinary programs stay in Type 0.
  • Higher levels matter when code talks about types and universes themselves.

Where Sort fits

Sort is Lean’s built-in universe constructor. It is not an ordinary type alias or runtime function.

Sort 0 = Prop
Sort 1 = Type 0
Sort 2 = Type 1
Sort 3 = Type 2

Type u is Lean’s friendlier notation for Sort (u + 1):

Sort u
├── u = 0       → Prop
└── u = n + 1   → Type n

The u in a declaration is a universe parameter. Lean resolves it while checking the program; it is not runtime data.

Prop is the special center

P : Prop
h : P

P = a proposition/type
h = a proof/value of P
  • Prop is the universe used for logical statements.
  • Its inhabitants include True, False, equalities, and bounds claims.
  • The inhabitants of one proposition are its proofs.
  • Lean treats proofs as proof-irrelevant: which proof we used does not change the truth of the proposition.
  • That special logical behavior is why Prop is more than merely “the smallest ordinary data universe.”

Back to DecidableEq

abbrev DecidableEq (α : Sort u) :=
  (a b : α) → Decidable (a = b)

The universe annotation says:

α : Sort u
    └── α may come from Prop, Type 0, Type 1, or a higher level

For our early GPU models, the practical picture stays small:

Nat       : Type 0
Thread1D  : Type 0
Array Nat : Type 0
x < size  : Prop

Pocket model

value → type → universe → next universe

inner levels remain usable outside
each universe itself lives one level up
Prop is the special logical center

Inspecting generated Lean code

The question

When Lean generates code for us, how do we find it and read it?

source declaration
      │
      ▼
macros + elaboration + deriving
      │
      ▼
named declarations in Lean's environment
      │
      ▼
discover with #synth → inspect with #print

For our first example:

structure Thread1D ...
deriving DecidableEq
          │
          ▼
instDecidableEqThread1D
          │
          ▼
instDecidableEqThread1D.decEq

Macro expansion versus elaboration

  • A macro transforms Lean syntax into other Lean syntax.
  • An elaborator turns convenient syntax into checked declarations and core terms.
  • A deriving handler inspects a declared type and adds new declarations.
  • deriving DecidableEq uses a deriving handler; it is not merely a textual macro.
macro             Syntax → Syntax
elaborator        Syntax → checked term / environment change
deriving handler  declared type → generated definitions + instances

Lean does not provide one cargo expand command that reconstructs the whole module as a new .lean file. We inspect the declarations added to the environment instead.

Step 1 — ask which instance Lean found

Put this after importing the module:

#synth DecidableEq LeanGpuLab.Lessons.ThreadIndex.Thread1D

Lean answers:

LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D
  • #synth runs typeclass-instance search.
  • Its output gives us the generated declaration’s real name.
  • Do not guess generated names when Lean can tell us directly.

Step 2 — inspect the instance

#print LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D

The important part of the output is:

def instDecidableEqThread1D : DecidableEq Thread1D :=
  instDecidableEqThread1D.decEq

That tells us the instance is a small wrapper around another generated function named .decEq.

Step 3 — inspect the generated function

#print LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D.decEq

#synth DecidableEq Thread1D
        │ reveals
        ▼
instDecidableEqThread1D
        │ #print reveals
        ▼
instDecidableEqThread1D.decEq
        │ #print reveals
        ▼
field-by-field implementation

If normal printing hides proof arguments behind ⋯, use:

Dissecting deriving DecidableEq

Starting point

structure Thread1D where
  blockIdx : Nat
  threadIdx : Nat
deriving Repr, DecidableEq

The rough Rust counterpart is familiar:

#![allow(unused)]
fn main() {
#[derive(Debug, PartialEq, Eq)]
struct Thread1D {
    block_idx: usize,
    thread_idx: usize,
}
}

Rust’s PartialEq derive and Lean’s DecidableEq derive both compare fields. Rust’s PartialEq::eq returns a bool; Lean returns a decision carrying proof that equality is true or false. Here usize is only illustrative: unlike Nat, it has a fixed machine width.

Read the target from the inside out

For Thread1D, Lean generates a value of this type:

(left right : Thread1D) → Decidable (Eq left right)

Build it one layer at a time:

Eq left right
    │ the equality proposition
    ▼
Decidable (Eq left right)
    │ a proved yes-or-no answer
    ▼
(left right : Thread1D) → Decidable (Eq left right)
    │ a function that produces that answer for every pair
    ▼
DecidableEq Thread1D
    the abbreviation for the complete function type

1. Eq is the claim, not the comparison

inductive Eq : {α : Sort u} → α → α → Prop where
  | refl (a : α) : Eq a a
  • Eq a b is the proposition that a and b are equal.
  • Lean normally writes it as a = b.
  • Eq.refl a, usually written rfl, proves that a = a.
  • Eq itself contains no field-comparison algorithm.

Lean’s Eq a b is not the same construct as Rust’s Eq marker trait over PartialEq. A Rust a == b expression returns a bool, not a proof or refutation.

2. Decidable is the proof-carrying answer

class inductive Decidable (p : Prop) where
  | isFalse (h : Not p) : Decidable p
  | isTrue  (h : p)     : Decidable p

If the two levels in p : Prop followed by h : p are unfamiliar, read Propositions as types first.

Decidable p
├── isTrue  h    where h : p
└── isFalse h    where h : Not p

Not p := p → False

The negative branch carries a function that turns any supposed proof of p into a contradiction. The Prelude exports both constructor names, which is why generated code may write isTrue rather than Decidable.isTrue.

What class means here

class says: “Lean may automatically find and insert values of this type.”

class does one thing here: it lets Lean search for and insert a missing Decidable p value.

(d : Decidable p)    -- the caller must pass d
[d : Decidable p]    -- Lean searches for d and inserts it

For example:

def truthValue (p : Prop) [d : Decidable p] : Bool :=
  match d with
  | isTrue _  => true
  | isFalse _ => false

#eval truthValue (2 = 2)

The call supplies p but omits d. Lean searches declarations marked instance for a value of type Decidable (2 = 2) and inserts it. If none is available, Lean reports failed to synthesize Decidable p.

class does not contain the algorithm that decides p. It turns on the automatic lookup; an instance supplies a value or recipe that produces isTrue h or isFalse h.

In Rust, a T: Trait bound lets the compiler resolve trait operations through an impl. In Lean, [d : Decidable p] makes Lean supply the actual value d. The compiler automation is similar, but Decidable is not a Rust-style trait containing methods.

3. DecidableEq is the decision-function type

abbrev DecidableEq (α : Sort u) :=
  (a b : α) → Decidable (Eq a b)

For every a and b in α, the function returns a proof of a = b or a refutation ¬(a = b).

DecidableEq is a transparent function abbreviation, not a declaration made with class. When Lean sees [DecidableEq α], it unfolds the abbreviation:

[DecidableEq α]
        ↓
[(a b : α) → Decidable (a = b)]

The result is a function whose output, Decidable (a = b), is a class. Lean’s instance mechanism therefore accepts the whole comparison function as a value it can search for and insert. deriving creates and registers that function.

Rust’s PartialEq::eq is the nearest operation, but it returns bool. Ordinary Rust cannot give it a proof result indexed by the particular inputs.

LeanWhat it isNearest Rust idea
Eq a bproposition that these values are equalno direct built-in equivalent
Decidable pproof-carrying yes-or-no valuenot a trait; only its automatic lookup is trait-like
classmarker enabling lookup and insertion for square-bracket argumentscompiler resolving a trait bound through an impl
DecidableEq αalias for the comparison-function typefunction-type alias, operationally like PartialEq::eq
deriving DecidableEqgenerates and registers that function#[derive(PartialEq)], but Lean’s function returns proofs

For more on Sort u, see Type universes.

What deriving creates

The generated instance is a small wrapper around the decision function:

def instDecidableEqThread1D : DecidableEq Thread1D :=
  instDecidableEqThread1D.decEq

The deriving handler generates the function below. It is not merely doing a text substitution.

def instDecidableEqThread1D.decEq :
    (x x_1 : Thread1D) → Decidable (x = x_1) :=
  fun x x_1 =>
    match x, x_1 with
    | { blockIdx := a, threadIdx := a_1 },
      { blockIdx := b, threadIdx := b_1 } =>
        if h : a = b then
          h ▸
            if h : a_1 = b_1 then
              h ▸ isTrue
                (instDecidableEqThread1D.decEq._proof_1 a a_1)
            else
              isFalse
                (instDecidableEqThread1D.decEq._proof_2 a a_1 b_1 h)
        else
          isFalse
            (instDecidableEqThread1D.decEq._proof_3 a a_1 b b_1 h)

Here a and a_1 are the left block and thread fields; b and b_1 are the right ones. Each is a Nat, so Lean uses Nat’s existing DecidableEq instance:

unpack both Thread1D values
        │
        ▼
compare blockIdx
        ├── different → isFalse proof_3
        ▼ equal
compare threadIdx
        ├── different → isFalse proof_2
        ▼ equal
isTrue proof_1

The if branches carry evidence

In each generated if h : ..., the local name h has a different proof type in each branch:

then branch    h : a = b
else branch    h : Not (a = b)

In a true branch, h ▸ value transports value along the equality proof h. After Lean transports across both field equalities, the two structures have equal fields and rfl proves the complete equality.

The three generated proof helpers

HelperBranchWhat it proves
_proof_1both fields matchthe structure equals itself, using rfl
_proof_2thread fields differstructure equality would contradict that difference
_proof_3block fields differstructure equality would contradict that difference

Here are the complete declarations for reference.

_proof_1 — both fields match

theorem LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D.decEq._proof_1 :
    ∀ (a a_1 : Nat),
      { blockIdx := a, threadIdx := a_1 } =
      { blockIdx := a, threadIdx := a_1 } :=
  fun a a_1 => rfl

_proof_2 — the thread fields differ

theorem LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D.decEq._proof_2 :
    ∀ (a a_1 b : Nat),
      ¬a_1 = b →
      { blockIdx := a, threadIdx := a_1 } =
      { blockIdx := a, threadIdx := b } →
      False :=
  fun a a_1 b h n =>
    LeanGpuLab.Lessons.ThreadIndex.Thread1D.mk.noConfusion n
      fun blockIdx_eq threadIdx_eq => h threadIdx_eq

Read the final two arguments as:

h : ¬(a_1 = b)
n : Thread1D.mk a a_1 = Thread1D.mk a b

noConfusion n extracts the field equalities implied by n, including threadIdx_eq : a_1 = b. Because negation is a function, ordinary application finishes the contradiction:

h threadIdx_eq : False

The unused blockIdx_eq is not needed.

_proof_3 — the block fields differ

theorem LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D.decEq._proof_3 :
    ∀ (a a_1 b b_1 : Nat),
      ¬a = b →
      { blockIdx := a, threadIdx := a_1 } =
      { blockIdx := b, threadIdx := b_1 } →
      False :=
  fun a a_1 b b_1 h n =>
    LeanGpuLab.Lessons.ThreadIndex.Thread1D.mk.noConfusion n
      fun blockIdx_eq threadIdx_eq => h blockIdx_eq

This is the same argument using the contradictory block-field equality. Every branch therefore returns the required type:

isTrue  proof_1    : Decidable (Eq x x_1)
isFalse proof_2    : Decidable (Eq x x_1)
isFalse proof_3    : Decidable (Eq x x_1)

Part 2 — later connect the proofs to cuda-oxide

The destination

  • Rust remains the normal cuda-oxide kernel language.
  • cuda-oxide owns the compiler IR.
  • Lean receives a small, deterministic view of that IR.
  • The existing NVVM/PTX path stays intact.

Open the interactive Archify diagram · View its typed source

We get there in two small bridges

Bridge A — prove that the pieces connect

  • Let Lean construct and verify one tiny KernelIR program.
  • Serialize it through a small, versioned format.
  • A Rust adapter builds cuda-oxide’s standalone CodegenModule.
  • Compile the same vector-add kernel to PTX.
Lean KernelIR + theorem
          │
          ▼
versioned fixture → Rust adapter → cuda-oxide-codegen → PTX
  • This is the quickest end-to-end experiment.
  • It does not yet prove that the Rust adapter or PTX lowering preserves meaning.

Bridge B — make Rust kernels the source

  • Export the supported subset from compiler-owned MIR.
  • Run Lean as a proof sidecar or build gate.
  • Bind the proof result to the exact IR using a deterministic hash.
Rust kernel
    │
    ▼
canonical MIR ───────────────→ PTX
    │
    └→ KernelIR + hash → Lean check → certificate for that hash

KernelIR v0

Keep the first version deliberately boring:

Kernel
├── parameters
├── named buffers + lengths
└── body
    ├── local assignment
    ├── global load / store
    ├── integer arithmetic / comparison
    ├── if
    └── sequence
  • Include: 1D block/thread IDs, bounded buffers, locals, loads, stores, if, sequencing.
  • Use first: exact indices and integer elements.
  • Before machine claims: refine indices and values to fixed-width BitVec operations.
  • Reject: any operation outside the supported subset.

🚧 Not in v0:

  • floats;
  • raw pointer aliasing;
  • loops and calls;
  • shared memory and barriers;
  • atomics, warp operations, inline PTX, or weak memory.

Where the exporter belongs

The useful future checkpoint is cuda-oxide’s post-mem2reg dialect-mir, in SSA form, following its documented compiler pipeline:

  • Observe after mem2reg has promoted imported memory operations into clear SSA data flow.
  • Observe before annotated loop unrolling and lowering transform the compiler-owned IR.
  • Use a dedicated read-only observer—not a debug dump or mutating pass.
  • Fail closed when that checkpoint is unavailable; cuda-oxide’s full debug mode skips mem2reg and loop unrolling.

Trust boundary

✅ Lean theorem describes the decoded KernelIR semantics.
🧪 Golden and differential tests exercise translations.
⚠ MIR → KernelIR exporter is initially trusted.
⚠ KernelIR → cuda-oxide MIR is initially trusted.
⚠ cuda-oxide lowering, LLVM, PTX tools, driver, and hardware are trusted.
🚧 Floats, barriers, atomics, and weak memory are not modeled in v0.
  • Until refinement proofs exist, say “verified KernelIR”.
  • Do not say “verified Rust-to-PTX compiler.”

Design rules

  • Fail closed: unsupported input is an error, never unknown or a no-op.
  • Keep serialization stable, ordered, versioned, and source-located.
  • Prove one-thread results separately from whole-grid noninterference.
  • Give global and shared memory different address identities.
  • Keep cLean as inspiration only; its audited source has no visible reuse license.
