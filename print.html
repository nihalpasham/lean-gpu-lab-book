This chapter gets the lab back into your hands after a break. The first goal is deliberately small: open one theorem, inspect its goal, and make the project pass its checks.

How the pieces fit

Open the interactive Archify diagram · View its typed source

The short version:

Elan chooses.
Lake orchestrates.
Lean checks and compiles.

lean — roughly rustc

  • Reads .lean source files.
  • Elaborates convenient syntax into precise core terms.
  • Type-checks programs.
  • Sends theorem declarations through Lean’s small trusted kernel.
  • Produces .olean compiled modules.
  • Can also produce code used by native executables.

The important difference:

Rust build: program must type-check
Lean build: program and every theorem proof must type-check
  • A broken proof is a build error.
  • There is no separate “proof build” for ordinary Lean development.

elan — almost exactly rustup

  • Installs Lean toolchains.
  • Lets different projects use different Lean versions.
  • Reads the nearest lean-toolchain file automatically.
  • Provides proxy commands such as lean and lake on PATH.

In our local projects:

cLean/          → Lean 4.20.1
lean-gpu-lab/   → Lean 4.33.1

Useful check:

elan show

lake — roughly cargo

  • Creates projects.
  • Resolves package dependencies.
  • Tracks Lean module dependencies.
  • Builds libraries and executables incrementally.
  • Stores generated files under .lake/.

Type universes — the nested-circle picture

The picture

Lean’s universes are easiest to picture as filled, nested circles:

  • The center contains propositions.
  • Each outer level can use everything from the levels inside it.
  • Moving outward also lets Lean talk about the previous universe itself.

The same picture in terminal-friendly ASCII:

+------------------------------- Type 2 --------------------------------+
| +----------------------------- Type 1 ------------------------------+ |
| | +--------------------------- Type 0 ----------------------------+ | |
| | |         Nat · Bool · Thread1D · Prop                          | | |
| | |  +------------------------- Prop --------------------------+  | | |
| | |  |      True · False · 2 = 2 · x < array.size              |  | | |
| | |  +---------------------------------------------------------+  | | |
| | +---------------------------------------------------------------+ | |
| +-------------------------------------------------------------------+ |
+-----------------------------------------------------------------------+

This is a type-checking model, not a picture of runtime memory or literal set-theoretic containers.

Read the hierarchy as a chain

rfl
 │ proves
 ▼
(2 = 2)
 │ is a proposition in
 ▼
Prop
 │ lives in
 ▼
Type 0
 │ lives in
 ▼
Type 1
 │ lives in
 ▼
Type 2

In Lean notation:

rfl     : (2 = 2)
(2 = 2) : Prop
Prop    : Type 0
Type 0  : Type 1
Type 1  : Type 2
  • A term has a type: rfl : 2 = 2.
  • A proposition is a type in Prop: (2 = 2) : Prop.
  • A small data type lives in Type 0: Nat : Type 0.
  • A universe lives one level higher: Type 0 : Type 1.

Type with no number means Type 0.

The circles overlap on purpose

The universes are cumulative:

Type 0  ──usable as──▶  Type 1  ──usable as──▶  Type 2
  • Nat naturally lives in Type 0.
  • Lean may also use Nat where a type from Type 1 or Type 2 is expected.
  • The outer levels therefore do not contain completely different types.
  • A useful approximation is Type 0 ⊆ Type 1 ⊆ Type 2.

Think nested filled circles, not separate rings:

Good:  [ Type 2 [ Type 1 [ Type 0 [ Prop ] ] ] ]

Wrong: [ Prop ]  [ Type 0 ]  [ Type 1 ]  [ Type 2 ]

Why Lean keeps adding levels

Letting the universe of types contain itself would permit dangerous self-reference:

Not allowed

Type 0 : Type 0

Lean places each universe in the next one instead:

Type 0 : Type 1
Type 1 : Type 2
Type 2 : Type 3
  • This hierarchy prevents the logical paradoxes caused by Type : Type.
  • Most ordinary programs stay in Type 0.
  • Higher levels matter when code talks about types and universes themselves.

Where Sort fits

Sort is Lean’s built-in universe constructor. It is not an ordinary type alias or runtime function.

Sort 0 = Prop
Sort 1 = Type 0
Sort 2 = Type 1
Sort 3 = Type 2

Type u is Lean’s friendlier notation for Sort (u + 1):

Sort u
├── u = 0       → Prop
└── u = n + 1   → Type n

The u in a declaration is a universe parameter. Lean resolves it while checking the program; it is not runtime data.

Prop is the special center

P : Prop
h : P

P = a proposition/type
h = a proof/value of P
  • Prop is the universe used for logical statements.
  • Its inhabitants include True, False, equalities, and bounds claims.
  • The inhabitants of one proposition are its proofs.
  • Lean treats proofs as proof-irrelevant: which proof we used does not change the truth of the proposition.
  • That special logical behavior is why Prop is more than merely “the smallest ordinary data universe.”

Back to DecidableEq

abbrev DecidableEq (α : Sort u) :=
  (a b : α) → Decidable (a = b)

The universe annotation says:

α : Sort u
    └── α may come from Prop, Type 0, Type 1, or a higher level

For our early GPU models, the practical picture stays small:

Nat       : Type 0
Thread1D  : Type 0
Array Nat : Type 0
x < size  : Prop

Pocket model

value → type → universe → next universe

inner levels remain usable outside
each universe itself lives one level up
Prop is the special logical center

Inspecting generated Lean code

The question

When Lean generates code for us, how do we find it and read it?

source declaration
      │
      ▼
macros + elaboration + deriving
      │
      ▼
named declarations in Lean's environment
      │
      ▼
discover with #synth → inspect with #print

For our first example:

structure Thread1D ...
deriving DecidableEq
          │
          ▼
instDecidableEqThread1D
          │
          ▼
instDecidableEqThread1D.decEq

Macro expansion versus elaboration

  • A macro transforms Lean syntax into other Lean syntax.
  • An elaborator turns convenient syntax into checked declarations and core terms.
  • A deriving handler inspects a declared type and adds new declarations.
  • deriving DecidableEq uses a deriving handler; it is not merely a textual macro.
macro             Syntax → Syntax
elaborator        Syntax → checked term / environment change
deriving handler  declared type → generated definitions + instances

Lean does not provide one cargo expand command that reconstructs the whole module as a new .lean file. We inspect the declarations added to the environment instead.

Step 1 — ask which instance Lean found

Put this after importing the module:

#synth DecidableEq LeanGpuLab.Lessons.ThreadIndex.Thread1D

Lean answers:

LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D
  • #synth runs typeclass-instance search.
  • Its output gives us the generated declaration’s real name.
  • Do not guess generated names when Lean can tell us directly.

Step 2 — inspect the instance

#print LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D

The important part of the output is:

def instDecidableEqThread1D : DecidableEq Thread1D :=
  instDecidableEqThread1D.decEq

That tells us the instance is a small wrapper around another generated function named .decEq.

What #print actually shows

This is the post-elaboration definition shown by Lean, with only the line breaks adjusted:

def instDecidableEqThread1D.decEq :
    (x x_1 : Thread1D) → Decidable (x = x_1) :=
  fun x x_1 =>
    match x, x_1 with
    | { blockIdx := a, threadIdx := a_1 },
      { blockIdx := b, threadIdx := b_1 } =>
        if h : a = b then
          h ▸
            if h : a_1 = b_1 then
              h ▸ isTrue ⋯
            else
              isFalse ⋯
        else
          isFalse ⋯
  • #print displays the definition after elaboration.
  • h ▸ value transports or rewrites value using equality proof h.
  • ⋯ means the pretty-printer has hidden a proof term.

The deriving trace looks different because it shows the source-like command before that command is elaborated:

deriving handler emits `by subst h`
                  │
                  ▼ elaboration
core equality transport
                  │
                  ▼ #print
shown as `h ▸ ...`

A readable source-like equivalent

The following version gives the generated variables descriptive names and spells out the hidden proof branches. It is useful for understanding the algorithm, but it is not the literal text emitted by #print.

def instDecidableEqThread1D.decEq
    (left right : Thread1D) : Decidable (left = right) :=
  match left, right with
  | Thread1D.mk leftBlock leftThread,
    Thread1D.mk rightBlock rightThread =>
      if blockEqual : leftBlock = rightBlock then
        by
          subst blockEqual
          exact
            if threadEqual : leftThread = rightThread then
              by
                subst threadEqual
                exact isTrue rfl
            else
              isFalse (by
                intro structuresEqual
                injection structuresEqual
                apply threadEqual
                assumption)
      else
        isFalse (by
          intro structuresEqual
          injection structuresEqual
          apply blockEqual
          assumption)

The structure is straightforward:

unpack both Thread1D values
        │
        ▼
compare blockIdx
        ├── different → isFalse
        ▼ equal
compare threadIdx
        ├── different → isFalse
        ▼ equal
isTrue rfl

Reusable recipe

For any generated typeclass instance:

1. #synth WantedClass YourType
2. copy the declaration name Lean prints
3. #print that declaration
4. follow and #print any helper names in its body
5. enable the handler's trace only when #print is insufficient

The important rule:

discover names with Lean → inspect declarations → follow generated helpers

Dissecting deriving DecidableEq

Starting point

structure Thread1D where
  blockIdx : Nat
  threadIdx : Nat
deriving Repr, DecidableEq
  • Thread1D is an ordinary structure with two Nat fields.
  • deriving DecidableEq asks Lean to generate a decision procedure for equality between two Thread1D values.
Thread1D + deriving DecidableEq
                │
                ▼
Lean's DecidableEq deriving handler
                │
                ▼
instDecidableEqThread1D.decEq
                │
                ▼
(left right : Thread1D) → Decidable (left = right)

The function type being implemented

abbrev DecidableEq (α : Sort u) :=
  (a b : α) → Decidable (Eq a b)
  • DecidableEq α is a transparent alias for a function type.
  • A value of that type is the actual equality-decision function.
  • For Thread1D, Lean must generate:
(left right : Thread1D) → Decidable (Eq left right)

Lean normally prints Eq left right as:

left = right

left = right       means       Eq left right
¬(left = right)    means       Not (Eq left right)

Eq states equality; it does not compare fields

inductive Eq : α → α → Prop where
  | refl (a : α) : Eq a a
  • Eq a b forms the proposition that a and b are identical.
  • Eq.refl a constructs a proof of Eq a a.
  • rfl is the convenient spelling normally used for that constructor.
  • This definition contains no Thread1D or field-comparison algorithm.
Eq a b                  statement to prove or refute
Eq.refl a / rfl         proof that a equals itself
DecidableEq derivation  generated algorithm that compares values

Decidable carries the answer and its proof

class inductive Decidable (p : Prop) where
  | isFalse (h : Not p) : Decidable p
  | isTrue  (h : p)     : Decidable p

Decidable p
├── isTrue  h    h : p
└── isFalse h    h : Not p    where Not p := p → False
  • inductive gives it two enum-like constructors.
  • class makes decisions available through typeclass-instance search.
  • h is the proof carried by the selected constructor.
  • Lean’s Prelude exports isTrue and isFalse, so generated code may omit the Decidable. prefix.

Where the real comparison happens

Lean generated:

def instDecidableEqThread1D.decEq :
    (x x_1 : Thread1D) → Decidable (x = x_1) :=
  fun x x_1 =>
    match x, x_1 with
    | { blockIdx := a, threadIdx := a_1 },
      { blockIdx := b, threadIdx := b_1 } =>
        if h : a = b then
          h ▸
            if h : a_1 = b_1 then
              h ▸ isTrue
                (instDecidableEqThread1D.decEq._proof_1 a a_1)
            else
              isFalse
                (instDecidableEqThread1D.decEq._proof_2 a a_1 b_1 h)
        else
          isFalse
            (instDecidableEqThread1D.decEq._proof_3 a a_1 b b_1 h)

The two comparisons are:

if h : a = b then          -- compare blockIdx
if h : a_1 = b_1 then      -- compare threadIdx
  • Each field is a Nat.
  • Lean uses Nat’s existing DecidableEq instance to decide each field equality.
  • The if h : proposition then form binds:
    • h : proposition in the true branch;
    • h : Not proposition in the false branch.
unpack both structures
        │
        ▼
compare blockIdx using Nat's DecidableEq
        ├── different → isFalse proof_3
        ▼ equal
compare threadIdx using Nat's DecidableEq
        ├── different → isFalse proof_2
        ▼ equal
isTrue proof_1

What h ▸ does

h ▸ value rewrites or transports value using equality proof h.

block fields equal
      │ h ▸
      ▼
thread fields equal
      │ h ▸
      ▼
both structures now have identical fields
      │
      ▼
rfl proves the complete structures are equal

The three generated proof helpers

HelperBranchWhat it proves
_proof_1both fields matchthe structure equals itself, using rfl
_proof_2thread fields differcomplete structure equality would contradict that difference
_proof_3block fields differcomplete structure equality would contradict that difference

Here are the complete generated declarations for reference.

_proof_1 — both fields match

theorem LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D.decEq._proof_1 :
    ∀ (a a_1 : Nat),
      { blockIdx := a, threadIdx := a_1 } =
      { blockIdx := a, threadIdx := a_1 } :=
  fun a a_1 => rfl
  • The parameters are a and a_1.
  • Applying the theorem to both parameters returns a proof that the complete Thread1D value equals itself.

_proof_2 — the thread fields differ

theorem LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D.decEq._proof_2 :
    ∀ (a a_1 b : Nat),
      ¬a_1 = b →
      { blockIdx := a, threadIdx := a_1 } =
      { blockIdx := a, threadIdx := b } →
      False :=
  fun a a_1 b h n =>
    LeanGpuLab.Lessons.ThreadIndex.Thread1D.mk.noConfusion n
      fun blockIdx_eq threadIdx_eq => h threadIdx_eq

The generated lambda leaves inferred types implicit. Read its outer lambda as:

fun (a a_1 b : Nat)
    (h : ¬(a_1 = b))
    (n :
      { blockIdx := a, threadIdx := a_1 } =
      { blockIdx := a, threadIdx := b }) =>
  ...
  • n is a proof value whose type says the complete structures are equal.
  • noConfusion n supplies the inner lambda with proofs that corresponding constructor fields are equal:
n: Thread1D.mk a a₁ = Thread1D.mk a b
                    │
                    ▼
              noConfusion
                    │
                    ├── blockIdx_eq
                    └── threadIdx_eq : a₁ = b

The last expression is ordinary function application. Negation is a function type:

h            : ¬(a_1 = b)       -- the proof value h
             = (a_1 = b) → False
threadIdx_eq : a_1 = b

h threadIdx_eq : False

blockIdx_eq is unused here; the contradictory thread-field equality is enough.

_proof_3 — the block fields differ

theorem LeanGpuLab.Lessons.ThreadIndex.instDecidableEqThread1D.decEq._proof_3 :
    ∀ (a a_1 b b_1 : Nat),
      ¬a = b →
      { blockIdx := a, threadIdx := a_1 } =
      { blockIdx := b, threadIdx := b_1 } →
      False :=
  fun a a_1 b b_1 h n =>
    LeanGpuLab.Lessons.ThreadIndex.Thread1D.mk.noConfusion n
      fun blockIdx_eq threadIdx_eq => h blockIdx_eq
  • h says the two block fields are not equal.
  • Assuming the structures are equal would imply equal block fields.
  • That contradiction produces the Not (Eq x x_1) required by isFalse.

The result is always correctly typed:

isTrue  proof_1    : Decidable (Eq x x_1)
isFalse proof_2    : Decidable (Eq x x_1)
isFalse proof_3    : Decidable (Eq x x_1)

Part 2 — later connect the proofs to cuda-oxide

The destination

  • Rust remains the normal cuda-oxide kernel language.
  • cuda-oxide owns the compiler IR.
  • Lean receives a small, deterministic view of that IR.
  • The existing NVVM/PTX path stays intact.

Open the interactive Archify diagram · View its typed source

We get there in two small bridges

Bridge A — prove that the pieces connect

  • Let Lean construct and verify one tiny KernelIR program.
  • Serialize it through a small, versioned format.
  • A Rust adapter builds cuda-oxide’s standalone CodegenModule.
  • Compile the same vector-add kernel to PTX.
Lean KernelIR + theorem
          │
          ▼
versioned fixture → Rust adapter → cuda-oxide-codegen → PTX
  • This is the quickest end-to-end experiment.
  • It does not yet prove that the Rust adapter or PTX lowering preserves meaning.

Bridge B — make Rust kernels the source

  • Export the supported subset from compiler-owned MIR.
  • Run Lean as a proof sidecar or build gate.
  • Bind the proof result to the exact IR using a deterministic hash.

KernelIR v0

Keep the first version deliberately boring:

Kernel
├── parameters
├── named buffers + lengths
└── body
    ├── local assignment
    ├── global load / store
    ├── integer arithmetic / comparison
    ├── if
    └── sequence
  • Include: 1D block/thread IDs, bounded buffers, locals, loads, stores, if, sequencing.
  • Use first: exact indices and integer elements.
  • Before machine claims: refine indices and values to fixed-width BitVec operations.
  • Reject: any operation outside the supported subset.

🚧 Not in v0:

  • floats;
  • raw pointer aliasing;
  • loops and calls;
  • shared memory and barriers;
  • atomics, warp operations, inline PTX, or weak memory.

Where the exporter belongs

The useful future checkpoint is cuda-oxide’s post-mem2reg dialect-mir, in SSA form, following its documented compiler pipeline:

Open the interactive Archify diagram · View its typed source

  • Observe after mem2reg has promoted imported memory operations into clear SSA data flow.
  • Observe before annotated loop unrolling and lowering transform the compiler-owned IR.
  • Use a dedicated read-only observer—not a debug dump or mutating pass.
  • Fail closed when that checkpoint is unavailable; cuda-oxide’s full debug mode skips mem2reg and loop unrolling.

Trust boundary

✅ Lean theorem describes the decoded KernelIR semantics.
🧪 Golden and differential tests exercise translations.
⚠ MIR → KernelIR exporter is initially trusted.
⚠ KernelIR → cuda-oxide MIR is initially trusted.
⚠ cuda-oxide lowering, LLVM, PTX tools, driver, and hardware are trusted.
🚧 Floats, barriers, atomics, and weak memory are not modeled in v0.
  • Until refinement proofs exist, say “verified KernelIR”.
  • Do not say “verified Rust-to-PTX compiler.”

Design rules

  • Fail closed: unsupported input is an error, never unknown or a no-op.
  • Keep serialization stable, ordered, versioned, and source-located.
  • Prove one-thread results separately from whole-grid noninterference.
  • Give global and shared memory different address identities.
  • Keep cLean as inspiration only; its audited source has no visible reuse license.
