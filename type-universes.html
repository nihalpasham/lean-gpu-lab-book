Type universes — the nested-circle picture

The picture

Lean’s universes are easiest to picture as filled, nested circles:

  • The center contains propositions.
  • Each outer level can use everything from the levels inside it.
  • Moving outward also lets Lean talk about the previous universe itself.

The same picture in terminal-friendly ASCII:

+------------------------------- Type 2 --------------------------------+
| +----------------------------- Type 1 ------------------------------+ |
| | +--------------------------- Type 0 ----------------------------+ | |
| | |         Nat · Bool · Thread1D · Prop                          | | |
| | |  +------------------------- Prop --------------------------+  | | |
| | |  |      True · False · 2 = 2 · x < array.size              |  | | |
| | |  +---------------------------------------------------------+  | | |
| | +---------------------------------------------------------------+ | |
| +-------------------------------------------------------------------+ |
+-----------------------------------------------------------------------+

This is a type-checking model, not a picture of runtime memory or literal set-theoretic containers.

Read the hierarchy as a chain

rfl
 │ proves
 ▼
(2 = 2)
 │ is a proposition in
 ▼
Prop
 │ lives in
 ▼
Type 0
 │ lives in
 ▼
Type 1
 │ lives in
 ▼
Type 2

In Lean notation:

rfl     : (2 = 2)
(2 = 2) : Prop
Prop    : Type 0
Type 0  : Type 1
Type 1  : Type 2
  • A term has a type: rfl : 2 = 2.
  • A proposition is a type in Prop: (2 = 2) : Prop.
  • A small data type lives in Type 0: Nat : Type 0.
  • A universe lives one level higher: Type 0 : Type 1.

Type with no number means Type 0.

The circles overlap on purpose

The universes are cumulative:

Type 0  ──usable as──▶  Type 1  ──usable as──▶  Type 2
  • Nat naturally lives in Type 0.
  • Lean may also use Nat where a type from Type 1 or Type 2 is expected.
  • The outer levels therefore do not contain completely different types.
  • A useful approximation is Type 0 ⊆ Type 1 ⊆ Type 2.

Think nested filled circles, not separate rings:

Good:  [ Type 2 [ Type 1 [ Type 0 [ Prop ] ] ] ]

Wrong: [ Prop ]  [ Type 0 ]  [ Type 1 ]  [ Type 2 ]

Why Lean keeps adding levels

Letting the universe of types contain itself would permit dangerous self-reference:

Not allowed

Type 0 : Type 0

Lean places each universe in the next one instead:

Type 0 : Type 1
Type 1 : Type 2
Type 2 : Type 3
  • This hierarchy prevents the logical paradoxes caused by Type : Type.
  • Most ordinary programs stay in Type 0.
  • Higher levels matter when code talks about types and universes themselves.

Where Sort fits

Sort is Lean’s built-in universe constructor. It is not an ordinary type alias or runtime function.

Sort 0 = Prop
Sort 1 = Type 0
Sort 2 = Type 1
Sort 3 = Type 2

Type u is Lean’s friendlier notation for Sort (u + 1):

Sort u
├── u = 0       → Prop
└── u = n + 1   → Type n

The u in a declaration is a universe parameter. Lean resolves it while checking the program; it is not runtime data.

Prop is the special center

P : Prop
h : P

P = a proposition/type
h = a proof/value of P
  • Prop is the universe used for logical statements.
  • Its inhabitants include True, False, equalities, and bounds claims.
  • The inhabitants of one proposition are its proofs.
  • Lean treats proofs as proof-irrelevant: which proof we used does not change the truth of the proposition.
  • That special logical behavior is why Prop is more than merely “the smallest ordinary data universe.”

Back to DecidableEq

abbrev DecidableEq (α : Sort u) :=
  (a b : α) → Decidable (a = b)

The universe annotation says:

α : Sort u
    └── α may come from Prop, Type 0, Type 1, or a higher level

For our early GPU models, the practical picture stays small:

Nat       : Type 0
Thread1D  : Type 0
Array Nat : Type 0
x < size  : Prop
